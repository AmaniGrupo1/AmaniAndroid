    Capa UI y Sistema de Diseño¶

    Esta página describe la capa de interfaz de usuario construida íntegramente con Jetpack Compose y Material Design 3, abarcando el sistema de diseño en ui/theme/, los componentes reutilizables y la gestión de estados reactivos en presentation/.

    Sistema de diseño Material 3 (ui/theme/)¶

    El punto de entrada visual de la aplicación es el composable AppTheme, invocado desde MainActivity.onCreate():

    Archivo Responsabilidad
    Theme.kt Define AmaniLightColorScheme, AmaniDarkColorScheme, los tokens semánticos AmaniExtraColors (LocalAmaniColors) y el punto de entrada AppTheme (con alias ApplicationAmaniTheme).
    Color.kt Declara los tokens de color de marca (LightPrimary = #635A79, LightPrimaryContainer = #CCC0E4) y pares semánticos success/warning verificados con contraste WCAG 2.1 AA (DEC-01, DEC-05).
    Type.kt Configura la escala tipográfica Typography combinando Nunito (display, headline, titleLarge) y Roboto (body, label, titleMedium/Small) según DEC-03.
    Shape.kt y Spacing.kt Centralizan los radios de esquina (AmaniShapes) y espaciados consistentes.
    app/src/main/java/org/ies/tierno/applicationamani/ui/theme/Theme.kt
    CompositionLocalProvider(
    LocalAmaniColors provides extraColors,
) {
    MaterialTheme(
        colorScheme = colorScheme,
        typography = Typography,
        shapes = AmaniShapes,
        content = content,
    )
}

    Preferencia de tema y Dynamic Color

    AppTheme observa UserSessionDataStore.sessionFlow en tiempo real: si el usuario ha elegido modo claro u oscuro (session.tema), prevalece sobre el ajuste del sistema. Dynamic Color está desactivado (DEC-02) para preservar la identidad visual de Amani y los colores de estado de las citas.

    Pantallas por rol y componentes reutilizables¶

    Las pantallas se agrupan según el rol o dominio funcional dentro de presentation/ui/:

    • Acceso y onboarding: Principal.kt, LoginScreen.kt, RegisterScreen.kt, QuestionnaireScreen.kt.
    • Paciente (pacienteView/): ViewPacientePrincipalScreen.kt, CitasScreen.kt, AgendaCitaScreen.kt, EditarCitaScreen.kt, HistorialClinicoScreen.kt, SettingsOptionPaciente.kt.
    • Psicólogo (psicologoView/): ViewPsicologoPrincipal.kt, PsicologoAgendaScreen.kt, CrearHistorialClinicoScreen.kt, EstadisticasPsicologoScreen.kt, SettingsPsychologistScreen.kt.
    • Administrador (AdminView/): ViewAdminPrincipal.kt, ListadoPacientesScreen.kt, ListadoPsicologosScreen.kt, AgregaPsicologoScreen.kt, AdminUserManagementScreen.kt, TerapiasScreen.kt.
    • Módulos transversales: ChatListScreen.kt, ChatScreenV2.kt, DiarioEmocionalScreen.kt, PaymentScreen.kt, MisTicketsScreen.kt, SnakeScreen.kt.
    • Componentes reutilizables: AmaniBottomBar (barra inferior adaptada a BottomBarConfig.Paciente, Admin y Psicologo), ThemeModeSelector, AmaniEmptyState, AmaniPersonRow, BottomSheetCambiarRol y AudioBubbleV2.

    Playbook visual de pantallas activas¶

    Las rutas de NavGraph siguen Material 3 (con HIG de Apple solo como apoyo): listas con ListItem / AmaniPersonRow, vacíos con AmaniEmptyState (titleLarge + bodyMedium + icono onSurfaceVariant), lectura en bodyLarge, barras en titleLarge, metadatos sin alfa extra, objetivos táctiles ≥ 48 dp y copy en sentence case. Los ajustes no usan chevron de iOS; los calendarios conservan ChevronLeft/ChevronRight para cambiar de mes.

    Tratamiento visual del chat¶

    La lista (ChatListScreen) usa ListItem de Material 3 (avatar, titular y texto de apoyo, objetivo táctil ≥ 48 dp, sin chevron de iOS). La sala (ChatScreenV2) aplica titleLarge en la barra, bodyLarge en el mensaje, burbujas primaryContainer / surfaceContainerHighest y fechas con rol de encabezado. El compositor (ChatInputBar) mantiene 48 dp, copy en sentence case y respeta «reducir movimiento» en el pulso de grabación.

    Gestión de UiState, eventos y ejemplo de flujo completo¶

    Los ViewModels modelan los estados de carga, éxito y error mediante clases selladas (sealed class) o data class inmutables emitidas por StateFlow. Un ejemplo representativo es el flujo de pagos con Stripe:

    1. Estado sellado (PaymentUiState.kt): modela explícitamente los estados Idle, Loading, PaymentReady, Success y Error.
    app/src/main/java/org/ies/tierno/applicationamani/presentation/viewmodels/payment/PaymentUiState.kt
    sealed class PaymentUiState {
    data object Idle : PaymentUiState()
    data object Loading : PaymentUiState()
    data class PaymentReady(
        val clientSecret: String,
        val paymentIntentId: String,
        val amount: java.math.BigDecimal,
        val currency: String,
    ) : PaymentUiState()
    data class Success(val paymentIntentId: String) : PaymentUiState()
    data class Error(val message: String) : PaymentUiState()
}
    1. Pantalla → ViewModel → Caso de uso → Repositorio → API: PaymentScreen observa viewModel.uiState, solicita crear el intento de pago a PaymentViewModel, que invoca CreatePaymentIntentUseCase → PaymentRepository → PaymentApiService (POST /api/payments/create-intent), y al completarse actualiza el estado de la cita mediante CitasViewModel.marcarCitaComoPagada(citaId).
